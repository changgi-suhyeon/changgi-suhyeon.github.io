# 모바일 청첩장 — 설계 문서

작성일: 2026-08-08
예식일: **2026-10-31 (토) 12:00** — 작성 시점 기준 D-84

---

## 1. 개요

직접 제작하는 모바일 청첩장. 카카오톡으로 링크를 전달하면 하객이 열어보고, 참석 여부를 남길 수 있다.

**성공 기준**

1. 2026-10-31 당일, 하객이 링크를 열었을 때 반드시 동작한다.
2. RSVP 응답이 유실되지 않는다. 실패했을 때 하객이 실패한 줄 안다.
3. 예식 이후에도 링크가 살아남아 기념물로 남는다.

**비목표 (명시적으로 제외)**

- 방명록 — 스팸·욕설 대응과 삭제 요청 처리 부담 대비 실익이 낮다.
- 하객 포토 드롭 — 구현 난이도가 가장 높고 예식 후 죽는 기능이다.
- 화환 배송 — 레퍼런스에 있으나 업체 제휴 광고이므로 자체 제작 청첩장에 넣을 이유가 없다.
- 포토부스 안내 — 실제 설치할 때만 의미가 있다.
- 다크 모드 — 청첩장은 고정 톤이 맞다. 오히려 강제 다크 반전을 막아야 한다.

## 2. 기술 스택 및 배포

| 영역 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Astro | 기본 JS 0, 아일랜드만 하이드레이션 |
| 컴포넌트 | React | 아일랜드에만 사용 |
| UI | shadcn/ui (Base UI 기반) | 폼·다이얼로그 등 최소 범위 |
| 사이트 호스팅 | GitHub Pages (public repo) | `changgi-suhyeon.github.io` — 유저 페이지, **루트 경로** |
| API | Cloudflare Workers | `*.workers.dev` |
| DB | Cloudflare D1 | RSVP 단일 테이블 |
| 봇 방어 | Cloudflare Turnstile | 무료, 동일 계정 |
| 이미지 | 로컬 sharp → webp, 레포에 커밋 | **R2 미사용** (§2.2) |

### 2.1 저장소와 배포 경로

저장소를 두 개로 분리한다.

| 저장소 | 공개 | 로컬 경로 | 용도 |
|---|---|---|---|
| `changgi-suhyeon.github.io` | public | `~/Desktop/Project/marriage-invitation` | Astro 사이트 |
| `marriage-invitation-worker` | private | `~/Desktop/Project/marriage-invitation-worker` | Cloudflare Worker + D1 |

- **사이트** — `main` 푸시 → GitHub Actions → `astro build` → `actions/deploy-pages`
- **Worker** — 로컬에서 `wrangler deploy`. 변경 빈도가 낮아 CI에 넣을 이유가 없다. 저장소가 분리되어도 배포 방식은 동일하다.

`changgi-suhyeon.github.io`는 프로젝트 페이지가 아니라 **유저 페이지** 저장소이므로 사이트가 `https://changgi-suhyeon.github.io/` 루트에 배포된다. 따라서 **Astro `base` 설정이 필요 없다.** `site: 'https://changgi-suhyeon.github.io'`만 지정하며, 에셋 경로가 서브패스를 신경 쓸 필요도 없다.

저장소 분리의 대가는 **API 계약이 두 저장소에 걸친다는 점**이다. RSVP 요청·응답 타입이 양쪽에 중복되므로, 한쪽만 고치면 조용히 어긋난다. 타입 정의를 사이트 저장소의 `src/lib/rsvp-contract.ts`에 두고 Worker 저장소가 이를 복사해 맞추되, **§8의 E2E 테스트가 실제 배포된 Worker를 호출하도록 해서 어긋남을 잡는다.**

### 2.2 R2를 쓰지 않는 이유

| 대상 | 용량 | 레포 수용 |
|---|---|---|
| 스튜디오 원본 JPG 30장 | 300~600MB | 불가 |
| 최적화 webp 3종 × 30장 | **약 10MB** | 가능 |

레포에 들어가는 것은 원본이 아니라 최적화 산출물이며 약 10MB다. GitHub Pages 사이트 한도 1GB에 한참 못 미치고, 하객 500명 × 3MB = 1.5GB로 월 대역폭 soft limit 100GB에도 근접하지 않는다.

R2가 정당해지는 조건(대역폭 폭증, 잦은 사진 교체)이 모두 해당되지 않는다. 나중에 필요해지면 **이미지 URL prefix 하나만 교체**하면 되므로 지금 지불할 복잡도가 아니다.

원본 JPG는 레포 밖에 보관한다. 클라우드 아카이브는 청첩장과 무관한 별개 니즈이므로 이 코드베이스와 엮지 않는다.

### 2.3 RSVP 백엔드를 Cloudflare로 정한 이유

청첩장 RSVP는 일반 웹 서비스와 트래픽 패턴이 다르다. **수 주간 요청 0 → 링크 배포 순간 동시 유입 → 예식 후 다시 0.**

- **Supabase 무료 티어** — 7일 무활동 시 프로젝트 일시정지. 개발 완료 후 배포까지의 공백 구간이 정확히 이 함정에 해당한다. GitHub Actions 크론 핑으로 막을 수 있으나, 크론이 조용히 실패하면 감지할 방법이 없다.
- **Oracle Cloud Always Free** — 콜드스타트는 없으나 TLS·프록시·systemd·백업을 직접 세우고 84일간 유지해야 하며, 유휴 인스턴스 회수 정책 리스크가 남는다. RSVP 폼 하나에 비해 과하다.
- **Google Apps Script** — CORS 제약으로 `no-cors` fire-and-forget이 되기 쉬워 제출 성공 여부를 하객에게 알릴 수 없다. 성공 기준 2번에 정면으로 위배된다.
- **Cloudflare Workers + D1 (채택)** — V8 isolate라 콜드스타트가 사실상 없고 일시정지 개념 자체가 없다. R2/DNS/Turnstile과 동일 계정. 무료 한도(Workers 10만 req/일, D1 5GB)가 이 규모의 수십 배다.

성공 기준 1번("당일 반드시 동작")이 **운영 노력이 아니라 구조에서 나오는** 유일한 선택지다.

### 3.2 데이터 흐름

**빌드 타임**
```
원본 JPG (레포 밖) ──sharp──> webp 3종 + LQIP ──┐
wedding.ts ─────────────────────────────────────┼──> astro build ──> GitHub Pages
Astro 섹션 + React 아일랜드 ────────────────────┘
```

사진 최적화는 매 빌드가 아니라 수동 1회다. 산출물을 커밋해두고 사진이 바뀔 때만 다시 돌린다.

**런타임 ① — 하객 제출**
```
RSVP 폼 ──POST──> [origin 확인 → Turnstile 검증 → 필드 검증 → 레이트리밋] ──> Worker ──> D1
```

**런타임 ② — 응답 조회**
```
/admin ──GET + Bearer──> [토큰 대조] ──> Worker ──> D1 ──> 목록·집계·CSV
```

`/admin`은 공개 정적 페이지다. **보안은 페이지를 숨기는 데서 오지 않고 토큰에서 온다.** 토큰은 Worker secret에만 있으므로 public repo여도 노출되지 않는다.

### 3.3 아일랜드 경계

기준: **상태가 있거나 브라우저 API가 필요한 것만 아일랜드.**

**정적 (JS 0)** — 히어로, 모시는 말씀·혼주, 오시는 길 텍스트, 식사·피로연, 전세버스, 푸터

추가로 정적으로 처리하는 것들:
- **캘린더** — 2026년 10월은 빌드 시점에 확정된 값이다. 런타임 계산할 이유가 없다.
- **연락하기** — 6명 × 전화/문자 링크 12개를 `<details>` 아코디언으로 접으면 JS 없이 모달과 동일한 UX가 나온다.
- **계좌 아코디언** — `<details>`. 복사 버튼만 아일랜드.
- **지도** — 정적 지도 이미지 + 지도앱 3종 딥링크. 카카오맵 SDK는 200KB 이상이며 초기화가 느린데, 실제 하객은 지도를 조작하기보다 앱으로 튀어나간다. 인터랙티브가 필요해지면 나중에 아일랜드로 전환.

**React 아일랜드**

| 컴포넌트 | 지시자 | 이유 |
|---|---|---|
| D-day 카운트다운 | `client:visible` | 타이머 |
| 갤러리 라이트박스 | `client:visible` | 상태 + 제스처 |
| 계좌 복사 버튼 | `client:visible` | Clipboard API |
| RSVP 폼 | `client:visible` | 폼 상태 + 네트워크 |
| 공유 버튼 | `client:idle` | Kakao SDK |
| BGM 토글 | `client:idle` | Audio |

## 4. 디자인 시스템

**방향: 클래식 정갈 + 그레이지** (레퍼런스 `areum.co.kr/invitation/basic-2` 계열에서 채도와 액센트 대비를 낮춘 톤)

### 4.1 색 토큰

| 토큰 | 값 | 용도 |
|---|---|---|
| `--bg` | `#F4F3F0` | 배경 |
| `--line` | `#D5D2CA` | 보더·구분선 |
| `--muted` | `#9B978D` | 라벨·보조 텍스트 |
| `--ink` | `#35342F` | 제목·본문 강조 |
| `--body` | `#6C6A64` | 본문 |

색 결정은 이 5개 변수에만 존재한다. 톤을 바꿀 때 변수 값만 교체하면 전체가 따라온다. 컴포넌트에 색을 하드코딩하지 않는다.

### 4.2 타이포

**명조 통짜는 쓰지 않는다.** 명조는 획이 얇아 모바일 본문 크기에서 가독성이 떨어지며, 어른 하객 비중을 고려하면 더 그렇다.

- **명조** — 이름, 섹션 타이틀, 인사글
- **산세리프** — 본문, 라벨, 버튼, 날짜·주소 등 정보성 텍스트

### 4.3 폰트 서브셋

청첩장은 **화면에 나올 글자가 빌드 시점에 전부 확정**되므로 완전 서브셋이 가능하다. 한글 웹폰트 통짜 300~400KB → 20~50KB.

**주의:** RSVP 폼에 하객이 직접 입력하는 이름은 서브셋에 없는 글자일 수 있어 깨진다. **폼과 `/admin`은 서브셋 폰트를 쓰지 않고 시스템 산세리프를 사용한다.** 폼은 산세리프가 가독성도 낫다.

### 4.4 강제 다크 모드 방지

삼성 인터넷·안드로이드 크롬의 "강제 어둡게"가 색을 반전시키면 톤 설계가 무의미해진다. `<meta name="color-scheme" content="light">`와 CSS `color-scheme: light`로 명시적으로 차단한다.

## 5. 페이지 구성

11개 섹션 + 고정 BGM 토글. 위에서 아래 순서.

### 5.1 섹션 순서와 근거

```
1. 히어로
2. 모시는 말씀 + 혼주 + 연락하기
3. 캘린더 + D-day
4. 갤러리
5. 오시는 길
6. 식사 · 피로연 안내
7. 전세버스 안내
8. RSVP          ← 레퍼런스보다 위로 이동
9. 마음 전하는 곳 (계좌)
10. 공유
11. 푸터
```

레퍼런스는 `계좌 → 방명록 → RSVP` 순이나, RSVP를 맨 끝에 두면 도달률이 떨어진다. RSVP는 하객에게 무언가를 *요청*하는 유일한 섹션이므로 위치가 중요하다.

**참석 판단에 필요한 정보(일시·장소·식사·버스)를 모두 제공한 직후**로 올린다. 계좌는 그 뒤에 두는 편이 순서상 부담이 적다.

### 5.2 섹션별 상세

**1. 히어로** — `THE MARRIAGE OF` 라벨 / 구분선 / 이름 / 일시 / 식장 / 아치형 메인 사진. 메인 사진이 LCP 대상이므로 `preload` + `fetchpriority="high"`, 나머지 사진은 전부 lazy. `100vh`는 모바일 주소창 문제로 사용하지 않는다.

**2. 모시는 말씀** — 인사글, 혼주 및 신랑·신부 표기, 연락하기 `<details>`(전화·문자 각 6명). 부모님 중 고인이 계실 경우 성함 앞 국화 표시가 관례이므로 `wedding.ts`에 플래그로 둔다.

**3. 캘린더 + D-day** — 2026년 10월 달력을 빌드 시점에 렌더하고 31일을 마크. 카운트다운만 아일랜드.

D-day는 **세 가지 상태**를 가진다. 이 처리를 빠뜨리면 11월에 들어온 사람에게 `D--5`가 표시된다. 청첩장 링크는 예식 후에도 카톡 대화방에 남아 계속 유입된다.

| 상태 | 표시 | RSVP |
|---|---|---|
| 예식 전 | `D-84` + 시:분:초 | 정상 |
| 당일 | "오늘 저희가 결혼합니다" | 정상 |
| 이후 | "저희 결혼식이 무사히 끝났습니다. 함께해 주셔서 감사합니다" | **마감 안내로 대체** |

세 번째 상태가 이 사이트를 청첩장에서 기념물로 전환시키는 지점이다.

**4. 갤러리** — 3열 정사각 그리드, 탭하면 라이트박스. 사진 장수는 미정이며 **장수와 무관하게 동작하도록 배열 기반으로 구현**한다. 권장 15~30장(초과 시 스크롤 피로로 완주율이 떨어짐).

라이트박스 요구사항:
- **안드로이드 뒤로가기 = 닫기.** history state를 쌓아 매핑한다. 처리하지 않으면 뒤로가기가 페이지를 떠나버린다.
- body 스크롤 잠금, 좌우 스와이프, 핀치 줌, ESC 닫기
- `prefers-reduced-motion` 존중

**5. 오시는 길**

```
L65호텔웨딩컨벤션
서울 동대문구 왕산로 200
청량리역 롯데캐슬스카이-L65 타워동 6층 가든홀
```

정적 지도 이미지 + 지도앱 3종(카카오맵·네이버지도·티맵) 딥링크. 그 아래 `<details>` 아코디언.

식장이 **청량리역 직결**이므로 대중교통 안내가 단순해진다. 청량리역은 지하철 1호선·경의중앙선·수인분당선 환승역이자 KTX·ITX가 정차하는 철도 거점이다. **지방 하객이 기차로 접근하기 좋은 위치이므로 "기차로 오시는 길"을 대중교통 아코디언에 별도 항목으로 둔다.**

아코디언 구성: `지하철 · 버스` / `기차` / `자가용 · 주차`

> 노선 번호, 출구 번호, 주차 시간·요금 등 세부 정보는 `wedding.ts`에 채워 넣는다. 확정 전까지 플레이스홀더.

**6. 식사 · 피로연 안내** — 식사 형태, 이용 가능 시간, 별도 피로연이 있으면 장소·시간.

**7. 전세버스 안내** — 출발 시각, 승차 장소, 인솔 담당자 연락처(전화 링크). 청량리역 접근성이 좋으므로 5번의 기차 안내와 내용이 겹치지 않도록 대상을 명확히 구분해 작성한다.

**8. RSVP** — §6 참조.

**9. 마음 전하는 곳** — 신랑측/신부측 `<details>`. 각 은행·계좌·예금주 + 복사 버튼. 카카오페이 송금 링크는 있으면 optional로 추가.

**10. 공유** — 카카오톡 공유(Kakao JS SDK), 링크 복사.

**11. 푸터** — 이름과 날짜만. 저작권 표기는 불필요.

**BGM 토글** — 우상단 고정, **기본 off**. 모바일 브라우저가 자동재생을 차단하므로 수동 토글이 유일한 방법이다. 로열티 프리 음원을 사용한다.

### 5.3 전역 사항

- **스크롤 진입 애니메이션** — IntersectionObserver(섹션당 1회 후 unobserve). `prefers-reduced-motion` 존중. CSS scroll-driven animation은 구형 기기 지원 문제로 사용하지 않는다.
- **접근성** — 본문 최소 16px, 터치 타겟 최소 44px, 명조 텍스트 대비 확인. 어른 하객 기준으로 잡고 글자를 작게 만들지 않는다.
- **OG 메타** — 1200×630, 절대 URL.

## 6. RSVP

### 6.1 D1 스키마

```sql
CREATE TABLE rsvp (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at  TEXT    NOT NULL DEFAULT (datetime('now')),
  created_ms  INTEGER NOT NULL,   -- 레이트리밋 조회용
  side        TEXT    NOT NULL,   -- 'groom' | 'bride'
  name        TEXT    NOT NULL,
  attending   INTEGER NOT NULL,   -- 1 | 0
  party_size  INTEGER NOT NULL,   -- 본인 포함 총 인원
  meal_count  INTEGER NOT NULL,   -- 식사할 인원
  phone       TEXT,               -- 선택
  message     TEXT,               -- 선택
  ip_hash     TEXT                -- 해시만 저장, 원문 IP 미저장
);

CREATE INDEX idx_rsvp_created_ms ON rsvp(created_ms);
```

### 6.2 필드 설계

**"동반 인원"이라는 표현은 쓰지 않는다.** 본인 포함인지 제외인지 해석이 갈리며, 그 차이가 식대 정산 오차로 그대로 이어진다. 라벨을 **`본인 포함 총 참석 인원`**으로 명시하고 기본값 1.

**식사 인원을 별도로 받는다.** 참석하되 식사하지 않는 경우가 실제로 있다. 기본값은 참석 인원과 동일하되 줄일 수 있게 한다. 식장에 전달하는 숫자가 이것이다.

**불참 선택 시 인원·식사 필드를 숨긴다.** 불참인데 인원을 물으면 이탈한다.

**중복 제출을 막지 않는다.** 막으면 "잘못 입력했는데 고칠 수 없다"는 문의가 발생한다. 여러 건을 허용하고 관리자 페이지에서 동일 이름을 묶어 **최신 건 기준으로 집계**한다.

**개인정보 고지** — 폼 하단에 한 줄: "입력하신 정보는 예식 준비 목적으로만 사용하며 예식 후 파기합니다."

### 6.3 Worker API

| 메서드 | 경로 | 인증 |
|---|---|---|
| `POST` | `/rsvp` | Turnstile 토큰 |
| `GET` | `/rsvp` | `Authorization: Bearer <ADMIN_TOKEN>` |
| `OPTIONS` | `/rsvp` | CORS preflight |

**4관문**

| 관문 | 막는 것 | 한계 |
|---|---|---|
| Origin 확인 | 타 사이트에서의 호출 | 위조 가능. CSRF 수준 방어 |
| **Turnstile 검증** | 봇·자동 스팸 | **실질적 주력 방어** |
| 필드 검증 | 이상값, 과대 페이로드 | — |
| IP 해시 레이트리밋 | 수동 도배 | — |

브라우저 측 검증은 UX 목적이며 **서버는 클라이언트를 신뢰하지 않는다.**

검증 규칙: 이름 1~20자, 메시지 0~500자, `party_size` 1~10, `meal_count` 0 이상 `party_size` 이하, `side`는 열거값, `attending`은 불리언.

레이트리밋 규칙: 동일 `ip_hash`의 최근 10분 내 제출 건수가 5건을 넘으면 429를 반환한다. `idx_rsvp_created_ms`로 조회한다. 가족이 한 기기로 여러 명의 응답을 대신 넣는 경우를 막지 않을 만큼 느슨하게 잡은 값이다.

CORS는 와일드카드가 아닌 정확한 origin만 허용한다. 관리자 토큰 비교는 타이밍 세이프하게 수행한다.

시크릿은 `wrangler secret put`으로 주입하며 레포에 남기지 않는다:
- `ADMIN_TOKEN`
- `TURNSTILE_SECRET`

### 6.4 에러 처리

**RSVP가 실패했는데 하객이 성공한 줄 아는 것이 최악의 시나리오다.** 그 사람 몫의 식사가 잡히지 않는다.

| 상황 | 처리 |
|---|---|
| 네트워크 실패 | **입력값 유지** + 재시도 버튼. 폼이 비워지면 다시 작성하지 않는다 |
| 검증 실패 | 필드 옆 인라인 메시지 |
| 성공 | 명확한 확인 화면 + "수정이 필요하면 다시 제출해주세요" |
| 재방문 | localStorage 플래그로 "이미 전달해주셨어요" 표시(수정 가능) |
| 반복 실패 | **"카카오톡으로 알려주세요" 대체 경로 제시.** 하객을 막다른 길에 가두지 않는다 |

**장애 격리** — Worker나 D1이 죽어도 청첩장 본문은 정적이므로 날짜·장소·지도·계좌가 모두 정상 표시된다. 고장 범위가 RSVP 폼 하나로 격리된다.

### 6.5 관리자 페이지 (`/admin`)

토큰 입력 → `sessionStorage`에 보관(공용 기기 대비로 localStorage를 쓰지 않는다).

- **상단 집계** — 총 응답, 참석/불참, 신랑측·신부측 인원, **식사 인원 합계**
- **목록** — 최신순, 동일 이름 하이라이트
- **CSV 다운로드** — **UTF-8 BOM 포함.** 미포함 시 엑셀에서 한글이 깨지는데, 이 파일은 식장에 전달할 산출물이다.

1. **Worker 검증 로직** — vitest 유닛. 필드 경계값, 레이트리밋, 토큰 인증. 이 프로젝트에서 유일한 로직다운 로직이다.
2. **D-day 상태 전환** — 순수 함수로 분리하고 **현재 시각을 인자로 주입**한다. 내부에서 `Date.now()`를 호출하면 예식 전/당일/이후 세 상태를 테스트할 수 없다.
3. **RSVP 제출 E2E** — Playwright 1개. 성공 경로 + 실패 후 재시도.
4. 레이아웃·갤러리는 수동 확인.

### 8.1 실기기 확인 (자동 테스트보다 우선)

**카카오톡 인앱 브라우저가 실질적 주력 브라우저다.** 하객 대부분이 카톡 링크로 진입하며, 일반 사파리·크롬과 동작이 다르다. Clipboard API가 제한될 수 있고 오디오 정책과 폰트 로딩 거동이 다르다.

→ **계좌 복사 실패 시 계좌번호를 길게 눌러 선택할 수 있는 폴백을 반드시 넣는다.** 여기서 복사가 안 되면 곧바로 실사고다.

확인 목록: 카카오톡 인앱 브라우저 / iOS Safari / 안드로이드 크롬 / 강제 다크 모드 ON / 저속 네트워크
